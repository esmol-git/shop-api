# Ревью среза A (категории)

Дата: 2026-10-31.  
Основание: код, миграция `20261031100000_add_categories`, unit/e2e.  
Не переписывает ADR 0005/0006 целиком — фиксирует пробелы и гейт до среза B.

## Вердикт

Срез A **функционально работает** для create/read/rename и дерева.  
«Зелёный CI» недостаточен как доказательство качества: матрица границ и контракта PATCH неполная; инварианты БД частично не закрыты; `CATEGORY_MAX_DEPTH` — константа без валидации конфигурации.

**До B:** закрыть блокеры и обязательные доработки ниже.  
Контракт B (Serializable на create/move/delete, повторы P2034) — **отдельное утверждение**, не часть правок A.

## Блокеры (исправить до B)

1. **PATCH no-op не соответствует согласованному контракту с details.**  
   Сейчас `name` обязателен → `PATCH {}` → **400**.  
   Нужно: как у product details — **200 + текущее тело**, без записи и без смены `updatedAt`; то же имя после нормализации — такой же no-op.

2. **Нет CHECK `parentId IS NULL OR parentId <> id`.**  
   Приложение на create не ставит self-parent (новый UUID), но прямой SQL незащищён. Добавить в миграцию (follow-up или amend, если ещё можно локально) + отразить в ADR 0006 как границу гарантий.

3. **Сортировка не детерминирована при одинаковых `name`.**  
   Сейчас только `name ASC` (БД и дерево). Зафиксировать **`name ASC, id ASC`** в `findAll` и в `buildCategoryTree`.

## Обязательные доработки (контракт / тесты / ADR)

### Контракт и документация

- В ADR 0006 (короткое уточнение): плоский список и дерево **возвращаются целиком** — ограничение v1, не обещание масштаба.
- Таблица «приложение vs БД» (unique, FK, self-parent CHECK, глубина — приложение, циклы — алгоритм B).
- `CATEGORY_MAX_DEPTH`: default 4; одна точка чтения; не от клиента; при выносе в env — валидация «положительное целое» на старте. Сейчас это `export const = 4` — либо оставить константой v1 с явным ADR-текстом, либо завести env с валидацией (предпочтительно не размазывать до B без нужды: **зафиксировать в ADR «константа v1 = 4»** и тест на использование одной константы).

### Недостающие тесты (минимум)

| Кейс | Сейчас |
|---|---|
| name длина 200 OK / 201 → 400 | только unit VO на 201 |
| slug длина 1 / 100 OK / 101 → 400; формат | нет e2e/DTO |
| parentId: omitted vs `null` → корень | нет явного |
| parentId не-UUID → 400 | нет |
| PATCH с `slug`/`parentId`/`id` → 400 | нет (ожидаемо forbidNonWhitelisted) |
| PATCH текущим именем → 200, `updatedAt` не меняется | нет |
| PATCH `{}` → 200 no-op | нет (после фикса блокера) |
| 5-й уровень: в БД нет строки с slug l5 | не assert |
| несколько корней; несколько детей одного родителя | слабо |
| каждый узел ровно раз в дереве; листья `children: []` | частично |
| порядок `name`, затем `id` | нет |
| `GET /categories/tree` не 400 как UUID | нет (smoke) |
| конфликт slug concurrent (две параллельные вставки) | нет |
| P2002 только slug → 409; прочий DB error не маскируется | unit маппера частично |

### Код

- `RenameCategoryUseCase`: при отсутствии изменения имени после trim — не вызывать `update`.
- `P2003` → `parent-not-found`: сейчас единственный FK — ок; при появлении других FK не маскировать (заметка для C+).

## Отложенные (не расширяют A)

- Serializable + retries на create/move/delete — **контракт B**.
- Гонки из матрицы B (цикл A↔B, create+углубление, delete+create child).
- Глубина create вне общей транзакции с будущим move — известный риск до протокола B.
- `findDepth` ходит по предкам запросами — приемлемо для A; в B — в одной транзакции / одним SQL.
- Ручной `sortOrder`, пагинация списка/дерева.
- Смена slug категории.
- Конкурентный тест с barrier’ом (не «голый» `Promise.all`).

## Гейт

A считается готовым к B, когда:

1. закрыты три блокера;
2. дописаны обязательные тесты и короткое уточнение ADR 0006;
3. `npm run ci` зелёный.

После этого — отдельное утверждение протокола B (Serializable, retries, матрица гонок), без смешивания с доработкой A.
